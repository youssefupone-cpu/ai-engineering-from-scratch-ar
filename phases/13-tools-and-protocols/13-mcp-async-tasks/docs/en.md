# Async Tasks (SEP-1686) — Call-Now, Fetch-Later for Long-Running Work

> يستغرق عمل الوكيل الحقيقي من دقائق إلى ساعات: CI تشغيل، وتوليف بحثي عميق، وتصدير الدفعات. تقوم مكالمات الأداة المتزامنة بإسقاط الاتصالات أو انتهاء المهلة أو حظر UI. SEP-1686، تم دمجها في 25-11-2025، تضيف المهام البدائية: يمكن زيادة أي طلب ليصبح مهمة، ويمكن جلب النتيجة لاحقًا أو بثها عبر إشعارات الحالة. ملاحظة مخاطر الانجراف: المهام تجريبية حتى H1 2026؛ SDK لا يزال يتم تصميم السطح وفقًا للمواصفات.

**النوع:** بناء
** اللغات: ** Python (stdlib، آلة حالة المهمة غير المتزامنة)
**المتطلبات:** المرحلة 13 · 07 (MCP الخادم)، المرحلة 13 · 09 (النقل)
**الوقت:** ~75 دقيقة

## Learning Objectives

- حدد متى يجب ترقية أداة من متزامنة إلى مهمة معززة (> 30 ثانية من العمل من جانب الخادم).
- متابعة دورة حياة المهمة: `working` → `input_required` → `completed` / `failed` / `cancelled`.
- استمرار حالة المهمة حتى لا تفقد الأعطال العمل أثناء الرحلة.
- قم بالاستطلاع `tasks/status` وجلب `tasks/result` بشكل صحيح.

## The Problem

تقوم أداة `generate_report` بإجراء عملية استخراج pipeline لعدة دقائق. الخيارات ضمن النموذج المتزامن:

1. اترك الاتصال مفتوحًا لمدة ثلاث دقائق. وسائل النقل عن بعد تسقطها. مهلة العملاء؛ تجميد واجهات المستخدم.
2. العودة فورًا مع عنصر نائب؛ مطالبة العميل باستقصاء نقطة نهاية مخصصة. يكسر MCP التوحيد.
3. أطلق النار وانسى؛ لا نتيجة.

لا شيء جيد. SEP-1686 يضيف رابعاً: زيادة المهام. يمكن وضع علامة على أي طلب (عادةً `tools/call`) كمهمة. يقوم الخادم بإرجاع معرف المهمة على الفور. يقوم العميل باستقصاء `tasks/status` وجلب `tasks/result` عند الانتهاء. تستمر حالة جانب الخادم في عمليات إعادة التشغيل.

## The Concept

### Task augmentation

يصبح الطلب مهمة عن طريق تعيين `params._meta.task.required: true` (أو ​​`optional: true`، يقرر الخادم). يستجيب الخادم على الفور بـ:

```json
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "_meta": {
      "task": {
        "id": "tsk_9f7b...",
        "state": "working",
        "ttl": 900000
      }
    }
  }
}
```

`ttl` هو وعد الخادم بالاحتفاظ بالحالة؛ بعد ttl يتم تجاهل نتيجة المهمة.

### Per-tool opt-in

يمكن أن تعلن التعليقات التوضيحية للأداة عن دعم المهمة:

- `taskSupport: "forbidden"` — تعمل هذه الأداة دائمًا بشكل متزامن. آمنة للأدوات السريعة.
- `taskSupport: "optional"` — قد يطلب العميل زيادة المهام.
- `taskSupport: "required"` — العميل MUST يستخدم زيادة المهام.

الأداة `generate_report` ستكون `required`. الأداة `notes_search` ستكون `forbidden`.

### States

```
working  -> input_required -> working  (loop via elicitation)
working  -> completed
working  -> failed
working  -> cancelled
```

آلة الحالة قابلة للإلحاق فقط: بمجرد `completed`، `failed`، أو `cancelled`، تصبح المهمة نهائية.

### Methods

- `tasks/status {taskId}` — إرجاع الحالة الحالية وتلميح التقدم.
- `tasks/result {taskId}` — حظر أو إرجاع 404 إذا لم يتم ذلك بعد.
- `tasks/cancel {taskId}` — العاجز؛ تجاهل الدول الطرفية.
- `tasks/list` — اختياري؛ تعداد المهام النشطة والمكتملة مؤخرًا.

### Streaming state changes

عندما يدعمه الخادم، يمكن للعميل الاشتراك في إشعارات الحالة:

```
server -> notifications/tasks/updated {taskId, state, progress?}
```

العملاء الذين يبثون بدلاً من الاستطلاع يتحسنون UX. يتم دائمًا دعم الاستقصاء باعتباره السطح الأدنى.

### Durable state

تتطلب المواصفات خوادم تعلن عن دعم المهمة لاستمرار الحالة. يجب ألا يؤدي العطل إلى فقدان النتائج المكتملة ضمن ttl. تتراوح المتاجر من SQLite إلى Redis إلى نظام الملفات. يستخدم الدرس 13 نظام الملفات.

### Cancellation semantics

`tasks/cancel` عاجز. إذا كانت المهمة في منتصف التنفيذ، فسيحاول الخادم التوقف (تحقق من الإلغاء التعاوني للمنفذ). إذا كان الطلب نهائيًا بالفعل، فسيتم رفض الطلب.

### Crash recovery

عند إعادة تشغيل عملية الخادم:

1. قم بتحميل كافة حالات المهام المستمرة.
2. قم بوضع علامة على أي `working` مهام توقفت عمليتها كـ `failed` مع وجود خطأ `CRASH_RECOVERY`.
3. احتفظ بـ `completed` / `failed` / `cancelled` لـ ttl الخاصة بهم.

### Async tasks plus sampling

يمكن للمهمة نفسها أن تستدعي `sampling/createMessage`. هذه هي الطريقة التي تعمل بها مهام البحث طويلة الأمد: يقوم مؤشر ترابط المهام الخاص بالخادم باختبار نموذج العميل حسب الحاجة، بينما يُظهر UI الخاص بالعميل المهمة كـ `working` مع تحديثات التقدم الدورية.

### Why this is experimental

تم شحن SEP-1686 في 25/11/2025 ولكن خريطة الطريق الأوسع تستدعي ثلاث مشكلات مفتوحة: أساسيات الاشتراك الدائمة، والمهام الفرعية (علاقات المهام بين الوالدين والطفل)، وتوحيد النتائج TTL. توقع أن تتطور المواصفات خلال عام 2026. يجب أن يتعامل كود الإنتاج مع المهام على أنها مستقرة فقط للحالة الشائعة ويحميها من التغييرات المستقبلية SDK للمهام الفرعية.

## Use It

`code/main.py` ينفذ مخزن مهام متين (مدعوم من نظام الملفات) وأداة `generate_report` تعمل في سلسلة رسائل في الخلفية. يقوم العملاء باستدعاء الأداة، والحصول على معرف المهمة على الفور، والاستقصاء `tasks/status` أثناء قيام العامل بتحديث التقدم، وجلب `tasks/result` عند الانتهاء. أعمال الإلغاء؛ تتم محاكاة التعافي من الأعطال عن طريق إيقاف مؤشر ترابط العامل وإعادة تحميل الحالة.

ما الذي يجب النظر إليه:

- استمرت حالة المهمة JSON إلى `/tmp/lesson-13-tasks/<id>.json`.
- حقل تحديثات مؤشر ترابط العامل `progress`؛ يظهر الاستطلاع أنها تتقدم.
- الإلغاء من جانب العميل يحدد حدثًا؛ يقوم العامل بالفحص والخروج مبكرا.
- حالة إعادة التحميل عند "التعطل" تشير إلى المهمة أثناء الرحلة على أنها `failed` مع `CRASH_RECOVERY`.

## Ship It

ينتج عن هذا الدرس `outputs/skill-task-store-designer.md`. بالنظر إلى أداة طويلة الأمد (البحث، والإنشاء، والتصدير)، تصمم المهارة مخزن المهام (شكل الحالة، وTTL، والمتانة)، وتختار علامة دعم المهمة الصحيحة، وترسم إشعارات التقدم.

## Exercises

1. قم بتشغيل `code/main.py`. ابدأ مهمة `generate_report`، وحالة الاستقصاء، ثم قم بإحضار النتيجة.

2. أضف مكالمة `tasks/cancel` في منتصف التشغيل. التحقق من تكريم العامل له وتصبح الدولة `cancelled`.

3. محاكاة التعافي من العطل: قم بإيقاف مؤشر ترابط العامل، وأعد تشغيل المُحمل، ولاحظ وضع الفشل `CRASH_RECOVERY`.

4. قم بتوسيع المتجر إلى SQLite. انتصارات المتانة هي نفسها؛ يتم فتح خيارات الاستعلام (أدرج جميع المهام من الجلسة X).

5. اقرأ منشور خارطة الطريق MCP لعام 2026. حدد المشكلة المفتوحة المتعلقة بالمهام التي من المرجح أن تؤثر على تصميم SDK API في العام المقبل.
