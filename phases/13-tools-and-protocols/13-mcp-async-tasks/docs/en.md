# المهام غير المتزامنة (SEP-1686) — الاتصال الآن، والجلب لاحقًا للعمل طويل الأمد
> يستغرق عمل الوكيل الحقيقي دقائق إلى ساعات: CI يتم تشغيله، وتوليف البحث العميق، وتصدير الدُفعات. تقوم استدعاءات الأداة المتزامنة بإسقاط الاتصالات أو انتهاء المهلة أو حظر UI. يضيف SEP-1686، الذي تم دمجه في 25/11/2025، مهمة بدائية: يمكن زيادة أي طلب ليصبح مهمة، ويمكن جلب النتيجة لاحقًا أو بثها عبر إشعارات الحالة. ملاحظة حول مخاطر الانجراف: المهام تجريبية حتى H1 2026؛ لا يزال سطح SDK قيد التصميم وفقًا للمواصفات.
**النوع:** بناء
** اللغات: ** Python (stdlib، آلة حالة المهمة غير المتزامنة)
**المتطلبات الأساسية:** المرحلة 13 · 07 (MCP الخادم)، المرحلة 13 · 09 (النقل)
**الوقت:** ~75 دقيقة
## أهداف التعلم
- حدد متى يجب ترقية أداة من متزامنة إلى مهمة معززة (> 30 ثانية من العمل من جانب الخادم).
- تابع دورة حياة المهمة: `working` → `input_required` → `completed` / `failed` / `cancelled`.
- استمرار حالة المهمة حتى لا تفقد الأعطال العمل أثناء الرحلة.
- قم باستقصاء `tasks/status` وإحضار `tasks/result` بشكل صحيح.
## المشكلة
تقوم أداة `generate_report` بإجراء عملية استخراج pipeline لعدة دقائق. الخيارات ضمن النموذج المتزامن:
1. اترك الاتصال مفتوحًا لمدة ثلاث دقائق. وسائل النقل عن بعد تسقطها. مهلة العملاء؛ تجميد واجهات المستخدم.
2. العودة فورًا مع عنصر نائب؛ مطالبة العميل باستقصاء نقطة نهاية مخصصة. يكسر توحيد MCP.
3. أطلق النار وانسى؛ لا نتيجة.
لا شيء جيد. SEP-1686 يضيف رابعًا: زيادة المهام. يمكن وضع علامة على أي طلب (عادة `tools/call`) كمهمة. يقوم الخادم بإرجاع معرف المهمة على الفور. يقوم العميل باستقصاء `tasks/status` وجلب `tasks/result` عند الانتهاء. تستمر حالة جانب الخادم في عمليات إعادة التشغيل.
##المفهوم
### زيادة المهام
يصبح الطلب مهمة عن طريق تعيين `params._meta.task.required: true` (أو `optional: true`، حسب ما يقرره الخادم). يستجيب الخادم على الفور بـ:
```json
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "_meta": {
      "task": {
        "id": "tsk_9f7b...",
        "state": "working",
        "ttl": 900000
      }
    }
  }
}
```

`ttl` هو وعد الخادم بالاحتفاظ بالحالة؛ بعد ttl يتم تجاهل نتيجة المهمة.
### الاشتراك لكل أداة
يمكن أن تعلن التعليقات التوضيحية للأداة عن دعم المهمة:
- `taskSupport: "forbidden"` — تعمل هذه الأداة دائمًا بشكل متزامن. آمنة للأدوات السريعة.
- `taskSupport: "optional"` — قد يطلب العميل زيادة المهام.
- `taskSupport: "required"` — يستخدم العميل MUST تعزيز المهام.
أداة `generate_report` ستكون `required`. أداة `notes_search` ستكون `forbidden`.
### الولايات
```
working  -> input_required -> working  (loop via elicitation)
working  -> completed
working  -> failed
working  -> cancelled
```

آلة الحالة قابلة للإلحاق فقط: مرة واحدة `completed`، `failed`، أو `cancelled`، تصبح المهمة نهائية.
### طُرق
- `tasks/status {taskId}` — يُرجع الحالة الحالية وتلميحًا للتقدم.
- `tasks/result {taskId}` — حظر أو إرجاع 404 إذا لم يتم ذلك بعد.
- `tasks/cancel {taskId}` — عاجز؛ تجاهل الدول الطرفية.
- `tasks/list` — اختياري؛ تعداد المهام النشطة والمكتملة مؤخرًا.
### تغييرات حالة البث
عندما يدعمه الخادم، يمكن للعميل الاشتراك في إشعارات الحالة:
```
server -> notifications/tasks/updated {taskId, state, progress?}
```

العملاء الذين يبثون بدلاً من الاستطلاع يتحسنون UX. يتم دائمًا دعم الاستقصاء باعتباره السطح الأدنى.
### حالة دائمة
تتطلب المواصفات خوادم تعلن عن دعم المهمة لاستمرار الحالة. يجب ألا يؤدي العطل إلى فقدان النتائج المكتملة ضمن ttl. تتراوح المتاجر من SQLite إلى Redis إلى نظام الملفات. يستخدم الدرس 13 نظام الملفات.
### دلالات الإلغاء
`tasks/cancel` عاجز. إذا كانت المهمة في منتصف التنفيذ، فسيحاول الخادم التوقف (تحقق من الإلغاء التعاوني للمنفذ). إذا كان الطلب نهائيًا بالفعل، فسيتم رفض الطلب.
### التعافي من الأعطال
عند إعادة تشغيل عملية الخادم:
1. قم بتحميل كافة حالات المهام المستمرة.
2. قم بوضع علامة على أي `working` من المهام التي توقفت عمليتها كـ `failed` مع وجود خطأ `CRASH_RECOVERY`.
3. احتفظ بـ `completed` / `failed` / `cancelled` لـ ttl الخاصة بهم.
### المهام غير المتزامنة بالإضافة إلى أخذ العينات
يمكن للمهمة نفسها أن تستدعي `sampling/createMessage`. هذه هي الطريقة التي تعمل بها مهام البحث طويلة الأمد: يقوم مؤشر ترابط المهام الخاص بالخادم باختبار نموذج العميل حسب الحاجة، بينما يُظهر UI الخاص بالعميل المهمة على أنها `working` مع تحديثات التقدم الدورية.
### لماذا هذا تجريبي
تم شحن SEP-1686 في 25/11/2025 ولكن خريطة الطريق الأوسع تستدعي ثلاث مشكلات مفتوحة: أساسيات الاشتراك الدائمة، والمهام الفرعية (علاقات المهام بين الوالدين والطفل)، وتوحيد النتيجة TTL. توقع أن تتطور المواصفات خلال عام 2026. يجب أن يتعامل كود الإنتاج مع المهام على أنها مستقرة فقط للحالة الشائعة والحماية من تغييرات SDK المستقبلية للمهام الفرعية.
## استخدمه
ينفذ `code/main.py` مخزن مهام متين (مدعوم من نظام الملفات) وأداة `generate_report` التي تعمل في سلسلة رسائل في الخلفية. يتصل العملاء بالأداة، ويحصلون على معرف المهمة على الفور، ويستقصون `tasks/status` بينما يقوم العامل بتحديث التقدم، ويجلبون `tasks/result` عند الانتهاء. أعمال الإلغاء؛ تتم محاكاة التعافي من الأعطال عن طريق إيقاف مؤشر ترابط العامل وإعادة تحميل الحالة.
ما الذي يجب النظر إليه:
- استمرت حالة المهمة JSON إلى `/tmp/lesson-13-tasks/<id>.json`.
- تحديثات مؤشر ترابط العامل `progress` الحقل؛ يظهر الاستطلاع أنها تتقدم.
- الإلغاء من جانب العميل يحدد حدثًا؛ يقوم العامل بالفحص والخروج مبكرا.
- تقوم حالة إعادة التحميل عند "التعطل" بوضع علامة على المهمة أثناء الرحلة على أنها `failed` مع `CRASH_RECOVERY`.
## اشحنها
ينتج هذا الدرس `outputs/skill-task-store-designer.md`. بالنظر إلى أداة طويلة الأمد (البحث، والإنشاء، والتصدير)، تصمم المهارة مخزن المهام (شكل الحالة، وTTL، والمتانة)، وتختار علامة دعم المهمة الصحيحة، وترسم إشعارات التقدم.
## تمارين
1. قم بتشغيل `code/main.py`. ابدأ مهمة `generate_report`، وحالة الاستقصاء، ثم قم بإحضار النتيجة.
2. أضف مكالمة `tasks/cancel` أثناء التشغيل. التحقق من تكريم العامل له وتصبح الدولة `cancelled`.
3. محاكاة التعافي من العطل: قم بإيقاف مؤشر ترابط العامل، وأعد تشغيل المُحمل، ولاحظ وضع الفشل `CRASH_RECOVERY`.
4. قم بتوسيع المتجر إلى SQLite. انتصارات المتانة هي نفسها؛ يتم فتح خيارات الاستعلام (أدرج جميع المهام من الجلسة X).
5. اقرأ منشور خارطة الطريق MCP لعام 2026. حدد المشكلة المفتوحة المتعلقة بالمهام التي من المرجح أن تؤثر على تصميم SDK API في العام المقبل.
