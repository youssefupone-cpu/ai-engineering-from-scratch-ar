# MCP الأمان II — OAuth 2.1، مؤشرات الموارد، النطاقات الإضافية
> تحتاج خوادم MCP البعيدة إلى ترخيص، وليس فقط المصادقة. تتوافق مواصفات 25-11-2025 مع OAuth 2.1 + PKCE + مؤشرات الموارد (RFC 8707) + البيانات التعريفية للموارد المحمية (RFC 9728). يضيف SEP-835 موافقة النطاق المتزايدة مع تفويض تصعيدي في 403 WWW-المصادقة. يطبق هذا الدرس التدفق التصاعدي كآلة حالة حتى تتمكن من رؤية كل قفزة.
**النوع:** بناء
** اللغات: ** Python (stdlib، محاكي جهاز حالة OAuth)
**المتطلبات الأساسية:** المرحلة 13 · 09 (النقل)، المرحلة 13 · 15 (الأمن 1)
**الوقت:** ~75 دقيقة
## أهداف التعلم
- تمييز خادم الموارد عن مسؤوليات خادم الترخيص.
- اتبع مسار رمز تفويض OAuth 2.1 المحمي بـ PKCE.
- استخدم `resource` (RFC 8707) وبيانات تعريف الموارد المحمية (RFC 9728) لمنع هجمات الوكلاء المرتبكين.
- تنفيذ التفويض التصاعدي: يستجيب الخادم للرقم 403 بـ WWW-المصادقة تطلب نطاقًا أعلى؛ يقوم العميل بإعادة المطالبة بموافقة المستخدم وإعادة المحاولة.
## المشكلة
تم شحن الخوادم البعيدة المبكرة MCP (ما قبل 2025) بمفاتيح API مخصصة أو حتى بدون مصادقة. تغلق مواصفات 25-11-2025 هذه الفجوة بملف تعريف OAuth 2.1 كامل.
ثلاثة احتياجات في العالم الحقيقي:
- **الخوادم البعيدة العادية.** يقوم المستخدم بتثبيت خادم MCP بعيد يمكنه الوصول إلى Notion / GitHub / Gmail. OAuth 2.1 مع PKCE هو الشكل الصحيح.
- **تصعيد النطاق.** قد يحتاج خادم الملاحظات الذي تم منحه `notes:read` لاحقًا إلى `notes:write` لاتخاذ إجراء محدد. بدلاً من إعادة تنفيذ التدفق بالكامل، تطلب عملية المتابعة (SEP-835) النطاق الإضافي.
- **منع نائب الخلط.** يحمل العميل رمزًا مميزًا على نطاق الجمهور للخادم A. الخادم A ضار ويحاول تقديم الرمز المميز إلى الخادم B. تثبت مؤشرات الموارد (RFC 8707) الرمز المميز على الجمهور المقصود.
OAuth 2.1 ليس جديدًا. الجديد هو ملف تعريف MCP: التدفقات المطلوبة المحددة (رمز التفويض + PKCE فقط؛ غير ضمني، ولا توجد بيانات اعتماد للعميل بشكل افتراضي)، ومؤشرات الموارد إلزامية في كل طلب رمزي، وبيانات تعريف الموارد المحمية المنشورة حتى يعرف العملاء إلى أين يذهبون.
##المفهوم
### الأدوار
- **العميل.** العميل MCP (Claude Desktop، Cursor، وما إلى ذلك).
- **خادم الموارد.** خادم MCP (الملاحظات، GitHub، Postgres، أيًا كان).
- **خادم التفويض.** إصدار الرموز المميزة. قد تكون نفس الخدمة مثل خادم الموارد أو IdP منفصل (Auth0، Keycloak، Cognito).
في الملف الشخصي لـ MCP، تكون خوادم الموارد والتفويض CAN هي نفس المضيف ولكن SHOULD يتم تمييزها عن طريق عناوين URL.
### رمز التفويض + PKCE
التدفق:
1. يقوم العميل بإنشاء `code_verifier` (عشوائي) و`code_challenge` (SHA256).
2. يقوم العميل بإعادة توجيه المستخدم إلى `/authorize?response_type=code&client_id=...&redirect_uri=...&scope=notes:read&code_challenge=...&resource=https://notes.example.com`.
3. يوافق المستخدم. يقوم خادم التفويض بإعادة التوجيه إلى `redirect_uri?code=...`.
4. يرسل العميل إلى `/token?grant_type=authorization_code&code=...&code_verifier=...&resource=...`.
5. يتحقق خادم التفويض من صحة تجزئة أداة التحقق مقابل الاختبار المخزن ويصدر رمز وصول.
6. يستخدم العميل الرمز المميز: `Authorization: Bearer ...` في كل طلب إلى خادم الموارد.
PKCE يمنع هجمات اعتراض رمز التفويض. تمنع مؤشرات الموارد الرمز المميز من أن يكون صالحًا في مكان آخر.
### بيانات تعريف الموارد المحمية (RFC 9728)
ينشر خادم الموارد مستند `.well-known/oauth-protected-resource`:
```json
{
  "resource": "https://notes.example.com",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["notes:read", "notes:write", "notes:delete"]
}
```

يكتشف العميل خادم الترخيص من خادم الموارد. تقليل التكوين — يحتاج العميل فقط إلى المورد URL.
### مؤشرات الموارد (RFC 8707)
تعمل المعلمة `resource` في طلب الرمز المميز على تثبيت الجمهور المستهدف للرمز المميز. يحتوي الرمز المميز الذي تم إصداره على `aud: "https://notes.example.com"`. يقوم خادم MCP آخر يتلقى هذا الرمز المميز بفحص `aud` ويرفضه.
### نموذج النطاق
النطاقات عبارة عن سلاسل مفصولة بمسافات. اصطلاحات MCP الشائعة:
- `notes:read`، `notes:write`، `notes:delete`
- `admin:*` لإمكانيات المشرف (استخدمه باعتدال)
- `profile:read` للهوية
يجب أن يكون اختيار النطاق هو الأقل امتيازًا: اطلب ما تحتاجه الآن، وكثفه عندما تحتاج إلى المزيد.
### ترخيص المتابعة (SEP-835)
يمنح المستخدم `notes:read`. يطلبون لاحقًا من الوكيل حذف ملاحظة. يستجيب الخادم:
```
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
    scope="notes:delete", resource="https://notes.example.com"
```

يرى العميل خطأ النطاق غير الكافي، ويطالب المستخدم بمربع حوار موافقة للنطاق الإضافي، وينفذ تدفق OAuth صغير له، ويعيد محاولة الطلب باستخدام الرمز المميز الجديد.
### التحقق من صحة جمهور الرمز المميز
كل طلب: يتحقق الخادم من `token.aud == self.resource_url`. عدم التطابق = 401. يؤدي هذا إلى إيقاف إعادة استخدام الرمز المميز عبر الخادم.
### الرموز قصيرة العمر والتناوب
تكون رموز الوصول SHOULD قصيرة الأجل (افتراضي لمدة ساعة واحدة). يتم تدوير رموز التحديث عند كل تحديث. يعالج العميل التحديث الصامت في الخلفية.
### لا يوجد عبور رمزي
تقوم خوادم أخذ العينات (المرحلة 13 · 11) MUST NOT بتمرير الرمز المميز للعميل إلى الخدمات الأخرى. طلب أخذ العينات هو الحدود.
### نائب منع الخلط
يرتبط الرمز بـ `aud`. يرتبط العميل بـ `client_id`. تم التحقق من صحة كل طلب ضد كليهما. تحظر المواصفات صراحةً نمط "تمرير الرمز المميز" القديم الذي كان شائعًا في الأنظمة البيئية للأدوات البعيدة قبل MCP.
### اكتشاف العميل ID
ينشر كل عميل MCP بيانات التعريف الخاصة به عند URL ثابت. يمكن لخوادم التفويض جلب مستند البيانات التعريفية للعميل لاكتشاف إعادة توجيه عناوين URI ومعلومات الاتصال. يؤدي هذا إلى إزالة تسجيل العميل اليدوي.
### البوابات وOAuth
توضح المرحلة 13 · 17 كيفية تعامل بوابة المؤسسة مع OAuth: تحتفظ البوابة ببيانات اعتماد للخوادم الأولية، ويتم إصدار الرموز المميزة للعميل عن طريق البوابة، ولا تترك الرموز المميزة الأولية البوابة أبدًا. وهذا يقلب نموذج الثقة - حيث يقوم المستخدمون بالمصادقة مع البوابة مرة واحدة؛ تتعامل البوابة مع تفويضات خادم N.
## استخدمه
`code/main.py` يحاكي تدفق OAuth 2.1 الكامل كجهاز حالة. ينفذ:
- PKCE أداة التحقق من الكود/إنشاء التحدي.
- تدفق رمز التفويض مع مؤشر الموارد.
- نقطة نهاية البيانات التعريفية للموارد المحمية.
- التحقق من صحة الرمز مع فحص الجمهور.
- خطوة المتابعة على `insufficient_scope`.
لا يوجد خادم HTTP في هذا الدرس؛ تعمل آلة الحالة في الذاكرة حتى تتمكن من تتبع كل قفزة. المرحلة 13 · درس البوابة 17 ينقلها إلى وسيلة نقل فعلية.

## تمارين
1. قم بتشغيل `code/main.py`. تتبع تدفق خطوة المتابعة ذات النطاقين. لاحظ القفزات التي تتكرر عند الصعود.
2. إضافة تدوير رمز التحديث: يُصدر كل تحديث رمز تحديث جديدًا ويبطل الرمز القديم. محاكاة رمز التحديث المسروق الذي يتم استخدامه بعد التدوير والتأكد من فشله.
3. قم بتنفيذ نقطة نهاية بيانات تعريف الموارد المحمية كاستجابة HTTP حقيقية باستخدام stdlib http.server. اعكس نقطة النهاية /mcp من الدرس 09.
4. تصميم تسلسل هرمي للنطاق لخادم GitHub MCP: قراءة الريبو، كتابة PR، الموافقة على PR، دمج PR، المشرف. استخدام خطوة المتابعة بين كل مستوى.
5. اقرأ RFC 8707 وRFC 9728. حدد الحقل الوحيد في 9728 الذي يستخدمه MCP بشكل مختلف عن مثال RFC. (تلميح: يتعلق الأمر بـ `scopes_supported`.)
