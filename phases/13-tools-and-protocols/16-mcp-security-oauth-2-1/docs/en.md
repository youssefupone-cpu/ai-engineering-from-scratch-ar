# MCP Security II — OAuth 2.1, Resource Indicators, Incremental Scopes

> تحتاج خوادم MCP البعيدة إلى ترخيص، وليس فقط المصادقة. تتوافق مواصفات 2025-11-25 مع OAuth 2.1 + PKCE + مؤشرات الموارد (RFC 8707) + بيانات تعريف الموارد المحمية (RFC 9728). SEP-835 يضيف موافقة النطاق المتزايدة مع تفويض تصعيدي على 403 WWW-المصادقة. يطبق هذا الدرس التدفق التصاعدي كآلة حالة حتى تتمكن من رؤية كل قفزة.

**النوع:** بناء
** اللغات: ** Python (stdlib، محاكي جهاز حالة OAuth)
**المتطلبات الأساسية:** المرحلة 13 · 09 (النقل)، المرحلة 13 · 15 (الأمن 1)
**الوقت:** ~75 دقيقة

## Learning Objectives

- تمييز خادم الموارد عن مسؤوليات خادم الترخيص.
- اتبع مسار رمز ترخيص OAuth 2.1 المحمي PKCE.
- استخدم `resource` (RFC 8707) وبيانات تعريف الموارد المحمية (RFC 9728) لمنع هجمات الوكلاء المرتبكين.
- تنفيذ التفويض التصاعدي: يستجيب الخادم للرقم 403 بـ WWW-المصادقة التي تطلب نطاقًا أعلى؛ يقوم العميل بإعادة المطالبة بموافقة المستخدم وإعادة المحاولة.

## The Problem

في وقت مبكر MCP (ما قبل 2025) تم شحن الخوادم البعيدة بمفاتيح API مخصصة أو حتى بدون مصادقة. تغلق مواصفات 25-11-2025 هذه الفجوة بملف تعريف OAuth 2.1 كامل.

ثلاثة احتياجات في العالم الحقيقي:

- **الخوادم البعيدة العادية.** يقوم المستخدم بتثبيت خادم MCP عن بعد يمكنه الوصول إلى Notion / GitHub / Gmail. OAuth 2.1 مع PKCE هو الشكل الصحيح.
- **تصعيد النطاق.** قد يحتاج خادم الملاحظات الذي تم منحه `notes:read` لاحقًا إلى `notes:write` لإجراء معين. بدلاً من إعادة تنفيذ التدفق بالكامل، تطلب الخطوة (SEP-835) النطاق الإضافي.
- **منع نائب الخلط.** يحمل العميل رمزًا مميزًا على نطاق الجمهور للخادم A. الخادم A ضار ويحاول تقديم الرمز المميز إلى الخادم B. تثبت مؤشرات الموارد (RFC 8707) الرمز المميز على الجمهور المقصود.

OAuth 2.1 ليس جديدًا. الجديد هو ملف تعريف MCP: التدفقات المطلوبة المحددة (رمز التفويض + PKCE فقط؛ غير ضمني، ولا توجد بيانات اعتماد للعميل بشكل افتراضي)، ومؤشرات الموارد إلزامية في كل طلب رمزي، وبيانات تعريف الموارد المحمية المنشورة حتى يعرف العملاء إلى أين يذهبون.

## The Concept

### Roles

- **العميل.** العميل MCP (كلود سطح المكتب، المؤشر، وما إلى ذلك).
- **خادم الموارد.** خادم MCP (ملاحظات، GitHub، Postgres، أيًا كان).
- **خادم التفويض.** إصدار الرموز المميزة. قد تكون نفس الخدمة مثل خادم الموارد أو IdP منفصل (Auth0، Keycloak، Cognito).

في الملف الشخصي لـ MCP، تكون خوادم الموارد والتفويض CAN هي نفس المضيف ولكن SHOULD يتم تمييزها عن طريق عناوين URL.

### Authorization code + PKCE

التدفق:

1. يقوم العميل بإنشاء `code_verifier` (عشوائي) و `code_challenge` (SHA256).
2. يقوم العميل بإعادة توجيه المستخدم إلى `/authorize?response_type=code&client_id=...&redirect_uri=...&scope=notes:read&code_challenge=...&resource=https://notes.example.com`.
3. User consents. Authorization server redirects to `redirect_uri?code=...`.
4. Client POSTs to `/token?grant_type=authorization_code&code=...&code_verifier=...&resource=...`.
5. Authorization server validates the verifier's hash against the stored challenge and issues an access token.
6. Client uses the token: `التفويض: الحامل...` في كل طلب إلى خادم الموارد.

PKCE يمنع هجمات اعتراض رمز التفويض. تمنع مؤشرات الموارد الرمز المميز من أن يكون صالحًا في مكان آخر.

### Protected-resource metadata (RFC 9728)

ينشر خادم الموارد مستند `.well-known/oauth-protected-resource`:

```json
{
  "resource": "https://notes.example.com",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["notes:read", "notes:write", "notes:delete"]
}
```

يكتشف العميل خادم الترخيص من خادم الموارد. يقلل التكوين — يحتاج العميل فقط إلى المورد URL.

### Resource indicators (RFC 8707)

تقوم المعلمة `resource` في طلب الرمز المميز بتثبيت الجمهور المستهدف للرمز المميز. يحتوي الرمز المميز على `aud: "https://notes.example.com"`. يقوم خادم MCP آخر يتلقى هذا الرمز المميز بالتحقق من `aud` ويرفضه.

### Scope model

النطاقات عبارة عن سلاسل مفصولة بمسافات. اصطلاحات MCP الشائعة:

- `notes:read`، `notes:write`، `notes:delete`
- `admin:*` لإمكانات الإدارة (استخدمها باعتدال)
- `profile:read` للهوية

يجب أن يكون اختيار النطاق هو الأقل امتيازًا: اطلب ما تحتاجه الآن، وكثفه عندما تحتاج إلى المزيد.

### Step-up authorization (SEP-835)

يمنح المستخدم `notes:read`. يطلبون لاحقًا من الوكيل حذف ملاحظة. يستجيب الخادم:

```
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
    scope="notes:delete", resource="https://notes.example.com"
```

يرى العميل خطأ النطاق غير الكافي، ويطالب المستخدم بمربع حوار موافقة للنطاق الإضافي، وينفذ تدفق OAuth صغير له، ويعيد محاولة الطلب باستخدام الرمز المميز الجديد.

### Token audience validation

كل طلب: يتحقق الخادم `token.aud == self.resource_url`. عدم التطابق = 401. يؤدي هذا إلى إيقاف إعادة استخدام الرمز المميز عبر الخادم.

### Short-lived tokens and rotation

رموز الوصول SHOULD تكون قصيرة الأجل (افتراضي لمدة ساعة واحدة). يتم تدوير رموز التحديث عند كل تحديث. يعالج العميل التحديث الصامت في الخلفية.

### No token passthrough

خوادم أخذ العينات (المرحلة 13 · 11) MUST NOT تمرير رمز العميل إلى الخدمات الأخرى. طلب أخذ العينات هو الحدود.

### Confused deputy prevention

يرتبط الرمز بـ `aud`. يرتبط العميل بـ `client_id`. تم التحقق من صحة كل طلب ضد كليهما. تحظر المواصفات بشكل صريح نمط "تمرير الرمز المميز" القديم الذي كان شائعًا في الأنظمة البيئية للأدوات البعيدة قبل MCP.

### Client ID discovery

ينشر كل عميل MCP بيانات التعريف الخاصة به عند URL ثابت. يمكن لخوادم التفويض جلب مستند البيانات التعريفية للعميل لاكتشاف إعادة توجيه عناوين URI ومعلومات الاتصال. يؤدي هذا إلى إزالة تسجيل العميل اليدوي.

### Gateways and OAuth

توضح المرحلة 13 · 17 كيفية تعامل بوابة المؤسسة مع OAuth: تحتفظ البوابة ببيانات اعتماد للخوادم الأولية، ويتم إصدار الرموز المميزة للعميل عن طريق البوابة، ولا تترك الرموز المميزة الأولية البوابة أبدًا. وهذا يقلب نموذج الثقة - حيث يقوم المستخدمون بالمصادقة مع البوابة مرة واحدة؛ تتعامل البوابة مع تفويضات خادم N.

## Key Terms

| مصطلح | ماذا يقول الناس | ماذا يعني في الواقع |
|------|----------------|-----------------------|
| أووث 2.1 | "OAuth الحديث" | الموحد RFC الذي يوجب PKCE ويمنع التدفق الضمني |
| PKCE | "إثبات الحيازة" | التحقق من الكود + تحدي هزيمة اعتراض كود التفويض |
| مؤشر الموارد | "جمهور الرمز" | RFC 8707 `resource` معلمة تثبيت الرمز المميز على خادم واحد |
| بيانات تعريف الموارد المحمية | "وثيقة الاكتشاف" | RFC 9728 `.well-known/oauth-protected-resource` |
| إذن خطوة بخطوة | "الموافقة المتزايدة" | SEP-835 تدفق لإضافة النطاقات حسب الطلب |
| `insufficient_scope` | "403 مع WWW-المصادقة" | إشارة الخادم لإعادة الموافقة على نطاق أكبر |
| نائب حائر | "إعادة استخدام الرمز المميز عبر الخدمات" | الهجوم حيث يقوم صاحب موثوق بإعادة توجيه رمز مميز بشكل غير لائق |
| رمز قصير الأجل | "رمز الوصول TTL" | حامل تنتهي صلاحيته بسرعة؛ تجديد رمز التحديث |
| نطاق التسلسل الهرمي | "مكدس الامتيازات الأقل" | نطاق متدرج مع تصعيد بين المستويات |
| العميل ID البيانات الوصفية | "مستند اكتشاف العميل" | URL حيث ينشر العميل بيانات تعريف OAuth الخاصة به |
