# كابستون 16 — GitHub الإصدار إلى PR الوكيل المستقل
> AWS وكلاء SWE البعيدون، ووكلاء خلفية المؤشر، وOpenAI Codex cloud، وGoogle Jules جميعهم يقدمون نفس شكل المنتج لعام 2026: قم بتسمية مشكلة، واحصل على PR. قم بتشغيل وكيل في بيئة حماية سحابية، وتحقق من اجتياز الاختبارات، ثم قم بنشر PR جاهز للمراجعة مع الأساس المنطقي. تعمل الأجزاء الصلبة على إعادة إنتاج بيئة بناء الريبو تلقائيًا، مما يمنع تسرب بيانات الاعتماد، ويفرض ميزانيات كل ريبو، ويتأكد من عدم قدرة الوكيل على الدفع بالقوة. يقوم هذا التتويج ببناء الإصدار المستضاف ذاتيًا ومقارنته بالتكلفة ومعدل النجاح بالبدائل المستضافة.
**النوع:** كابستون
**اللغات:** بايثون (الوكيل)، TypeScript (GitHub التطبيق)، YAML (الإجراءات)
**المتطلبات الأساسية:** المرحلة 11 (LLM الهندسة)، المرحلة 13 (الأدوات)، المرحلة 14 (الوكلاء)، المرحلة 15 (الحكم الذاتي)، المرحلة 17 (البنية التحتية)
**مراحل التنفيذ:** P11 · P13 · P14 · P15 · P17
**الوقت:** 30 ساعة
## مشكلة
يعد وكيل الترميز السحابي غير المتزامن فئة منتج منفصلة عن وكلاء الترميز التفاعلي (capstone 01). UX عبارة عن تصنيف GitHub. يمكنك تسمية مشكلة بـ `@agent fix this`، ويقوم العامل بالدوران في صندوق الحماية السحابي، واستنساخ الريبو، وإجراء الاختبارات، وتحرير الملفات، والتحقق، وفتح PR مع الأساس المنطقي للوكيل في النص. لا توجد حلقة تفاعلية، ولا محطة. AWS SWE الوكلاء البعيدون، ووكلاء خلفية المؤشر، OpenAI Codex cloud، وGoogle Jules، وFactory Droids، جميعهم يتقاربون في هذا الأمر.
التحديات الهندسية ملموسة: إعادة إنتاج البيئة (يجب على الوكيل إنشاء الريبو من الصفر دون صورة مطور مخبأة)، والاختبارات غير المستقرة (يجب إعادة تشغيلها أو عزلها)، وتحديد نطاق الاعتماد (تطبيق GitHub مع الحد الأدنى من الأذونات الدقيقة)، وإنفاذ الميزانية لكل ريبو يوميًا، وسياسة عدم الدفع بالقوة. يقيس التتويج معدل النجاح والتكلفة والسلامة مقابل البدائل المستضافة.
## مفهوم
المشغل هو خطاف ويب GitHub (تصنيف المشكلة أو تعليق PR). يقوم المرسل بإدراج العمل في ECS Fargate أو Lambda. يسحب العامل الريبو إلى وضع الحماية Daytona أو E2B باستخدام ملف Dockerfile عام يتم استنتاجه من الريبو (اللغة، الإطار). يقوم الوكيل بتشغيل حلقة mini-swe-agent أو SWE-agent v2 ضد Claude Opus 4.7 أو GPT-5.4-Codex. إنه يتكرر: قراءة التعليمات البرمجية، واقتراح الإصلاح، وتطبيق التصحيح، وإجراء الاختبارات.
التحقق هو خطوة النابضة. يجب أن يمر CI بالكامل في وضع الحماية قبل فتح PR. يتم حساب دلتا التغطية؛ إذا كان سالبًا يتجاوز الحد، فسيتم فتح PR ولكن يتم تسميته `needs-review`. يقوم الوكيل بنشر الأساس المنطقي كوصف PR بالإضافة إلى سلسلة رسائل `@agent` التي يمكن للمراجع تنفيذ الأمر ping للمتابعة.
يتم تحديد نطاق السلامة من خلال سطحين مختلفين GitHub: يوفر التطبيق رمز تثبيت قصير الأمد مع `workflows: read` ومحتويات الريبو الضيقة/PR نطاقات؛ تفرض حماية الفرع (وليس أذونات التطبيق) "عدم الكتابة المباشرة إلى `main`" و"عدم فرض الدفع" - لا تتم إضافة التطبيق مطلقًا إلى قائمة التجاوز. إن الوصول للقراءة فقط على نطاق المسار إلى `.github/workflows` ليس تطبيقًا أوليًا حقيقيًا GitHub، لذا يجب على قائمة السماح للوكيل في عمليات تحرير الملفات فرض ذلك على العامل. يتم فرض أسقف الميزانية لكل عملية إعادة شراء يوميًا لدى المرسل (على سبيل المثال، بحد أقصى 5 طلبات شراء لكل عملية إعادة شراء يوميًا، 20 دولارًا لكل PR).
## بنيان
```
GitHub issue labeled `@agent fix` or PR comment
            |
            v
    GitHub App webhook -> AWS Lambda dispatcher
            |
            v
    ECS Fargate task (or GitHub Actions self-hosted runner)
       - pull repo
       - infer Dockerfile (language, package manager)
       - Daytona / E2B sandbox with target runtime
       - clone -> git worktree -> agent branch
            |
            v
    mini-swe-agent / SWE-agent v2 loop
       Claude Opus 4.7 or GPT-5.4-Codex
       tools: ripgrep, tree-sitter, read/edit, run_tests, git
            |
            v
    verify CI passes in-sandbox + coverage delta check
            |
            v (verified)
    git push + open PR via GitHub App
       PR body = rationale + diff summary + trace URL
       label: needs-review
            |
            v
    operator reviews; can @-mention agent for follow-ups
```

## المكدس
- المشغل: GitHub تطبيق ذو رمز مميز؛ جهاز استقبال webhook عبر Lambda أو Fly.io
- العامل: ECS مهمة Fargate (أو GitHub مشغل الإجراءات المستضاف ذاتيًا)
- Sandbox: حاوية Daytona devcontainer أو E2B Sandbox لكل مهمة
- حلقة الوكيل: خط الأساس mini-swe-agent أو SWE-agent v2 عبر Claude Opus 4.7 / GPT-5.4-Codex
- الاسترجاع: خريطة repo-sitter + ripgrep
- التحقق: كامل CI في وضع الحماية + بوابة دلتا التغطية
- إمكانية الملاحظة: Langfuse مع أرشيف التتبع per-PR المرتبط من نص PR
- الميزانية: الحد الأقصى اليومي بالدولار لكل إعادة شراء؛ الحد الأقصى من العلاقات العامة لكل الريبو في اليوم الواحد
## بنائها
1. **GitHub التطبيق.** رمز التثبيت الدقيق: مشكلات القراءة+الكتابة، وطلبات السحب الكتابة، والمحتويات قراءة+كتابة، وقراءة سير العمل. تفرض حماية الفرع (السطح الوحيد الذي يمكنه القيام بذلك) "عدم الدفع المباشر إلى `main`" و"عدم الدفع بالقوة"؛ التطبيق ليس في قائمة التجاوز. يفرض العامل "عدم الكتابة تحت `.github/workflows`" كفحص قائمة السماح على الفرق المقترح، نظرًا لأن أذونات التطبيق GitHub ليست ضمن نطاق المسار.
2. **مستقبل الخطاف عبر الويب.** تقبل وظيفة Lambda تسمية المشكلة / PR خطافات الويب للتعليق. عوامل التصفية حسب التصنيف `@agent fix this`. يدخل في قائمة الانتظار حتى SQS.
3. **المرسل.** ينبثق المهام من SQS. يفرض ميزانية الريبو لكل يوم. تشغيل مهمة ECS Fargate باستخدام الريبو URL ونص الإصدار ووضع الحماية الجديد لـ Daytona.
4. **استدلال البيئة.** كشف اللغة (Python، Node، Go، Rust) ومدير الحزم (uv، pnpm، go mod، cargo). قم بإنشاء ملف Dockerfile سريعًا في حالة عدم وجوده.
5. **حلقة الوكيل.** mini-swe-agent أو SWE-agent v2 مع Claude Opus 4.7. الأدوات: ripgrep، وtree-sitter repo-map، وread_file، وedit_file، وrun_tests، وgit. الحدود الصارمة: التكلفة 20 دولارًا، وساعة حائط مدتها 30 دقيقة، و30 دورة للوكلاء.
6. **التحقق.** بعد انتهاء الحلقة، قم بتشغيل مجموعة الاختبار الكاملة في وضع الحماية. حساب دلتا التغطية عبر jacoco /cover.py. إذا كان CI باللون الأحمر: توقف، فلا تفتح PR. إذا انخفضت التغطية بأكثر من 2%: افتح PR بالتسمية `needs-review`.
7. **PR النشر.** دفع فرع الوكيل. افتح PR عبر GitHub API مع: العنوان، الأساس المنطقي، ملخص الفرق، التتبع URL، التكلفة، المنعطفات.
8. **نظافة بيانات الاعتماد.** يعمل العامل باستخدام رمز تثبيت التطبيق GitHub قصير الأمد. يتم فحص السجلات بحثًا عن الأسرار قبل أرشفتها.
9. **التقييم.** 30 مشكلة داخلية مصنفة متفاوتة الصعوبة. قياس معدل النجاح، PR الجودة (الحجم المختلف، النمط، التغطية)، التكلفة، زمن الوصول. قارن مع وكلاء خلفية المؤشر ووكلاء AWS البعيدين SWE بشأن نفس المشكلات.

## تمارين
1. أضف وضع "إصلاح الاختبار غير المستقر": تُجري التسمية `@agent stabilize-flake TestX` الاختبار 50 مرة في وضع الحماية وتقترح الحد الأدنى من التغيير الذي يعمل على استقراره.
2. قارن التكلفة مقابل وكلاء خلفية المؤشر في ثلاث مشكلات مشتركة. قم بالإبلاغ عن الأدوات التي تفوز بها.
3. تنفيذ لوحة معلومات الميزانية: تكلفة كل يوم لإعادة الشراء، وتكلفة كل مستخدم. التنبيه على الشذوذ.
4. أنشئ وضع "التشغيل التجريبي" الذي يفتح مسودة PR بدون تشغيل CI، حتى يتمكن المراجعون من فحص الخطة بسعر رخيص.
5. أضف سياسة الاحتفاظ: PR يتم حذف الفروع الأقدم من 7 أيام دون الدمج تلقائيًا.
## المصطلحات الرئيسية
| مصطلح | ماذا يقول الناس | ماذا يعني في الواقع |
|------|-|---------------------------------------|
| GitHub التطبيق | "هوية الروبوت ذات النطاق" | تطبيق بأذونات دقيقة + رمز تثبيت قصير الأمد |
| وكيل السحابة غير المتزامن | "وكيل الخلفية" | عامل غير تفاعلي يعمل في وضع الحماية السحابي، وليس محطة طرفية |
| الاستدلال البيئي | "توليف ملف Dockerfile" | كشف اللغة + مدير الحزم، وإنشاء ملف Dockerfile في حالة غيابه |
| التحقق | "CI-في وضع الحماية" | قم بتشغيل مجموعة الاختبار الكاملة داخل العامل قبل فتح PR |
| دلتا التغطية | "الحفاظ على التغطية" | التغيير في نسبة تغطية الاختبار من فرع القاعدة إلى فرع الوكيل |
| ميزانية كل الريبو | "السقف اليومي" | يتم فرض الحد الأقصى لعدد الدولارات وPR على المرسل |
| الأساس المنطقي | "PR شرح النص" | ملخص الوكيل لما تغير ولماذا؛ مطلوب في نص PR |
