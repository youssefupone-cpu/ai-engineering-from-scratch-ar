# Capstone 09 — وكيل ترحيل التعليمات البرمجية (لغة مستوى الريبو / ترقية وقت التشغيل)
> قام Amazon's MigrationBench (Java 8 إلى 17) وأداة ترحيل Google App Engine Py2-to-Py3 بتعيين شريط 2026. يقوم OpenRewrite الخاص بـ Moderne بإعادة كتابة AST الحتمية على نطاق واسع. يستهدف Grit نفس المشكلة مع نمط codemod DSL. يجمع نمط الإنتاج بين كليهما: ركيزة حتمية لإعادة الكتابة الآمنة بالإضافة إلى طبقة وكيل للحالات الغامضة، وصندوق حماية للإنشاءات لكل فرع، وأداة اختبار تتقلب باللون الأخضر قبل فتح PR. الهدف الرئيسي هو ترحيل 50 اتفاقية إعادة شراء حقيقية ونشر معدل النجاح مع تصنيف الفشل.
**النوع:** كابستون
**اللغات:** بايثون (الوكيل)، جافا / بايثون (الأهداف)، TypeScript (لوحة المعلومات)
** المتطلبات الأساسية: ** المرحلة 5 (NLP)، المرحلة 7 (المحولات)، المرحلة 11 (LLM الهندسة)، المرحلة 13 (الأدوات)، المرحلة 14 (الوكلاء)، المرحلة 15 (الحكم الذاتي)، المرحلة 17 (البنية التحتية)
**مراحل التنفيذ:** P5 · P7 · P11 · P13 · P14 · P15 · P17
**الوقت:** 30 ساعة
## مشكلة
يعد ترحيل التعليمات البرمجية على نطاق واسع أحد أنظف تطبيقات الإنتاج لوكلاء الترميز 2026. الحقيقة الأساسية واضحة (هل تمر مجموعة الاختبار بعد الترحيل؟)، والمكافآت حقيقية (ترحيل أسطول Java-8 هو مشروع على نطاق واسع)، والمعايير عامة (مجموعة MigrationBench 50-repo الفرعية). يتعامل OpenRewrite الخاص بـ Moderne مع الجانب الحتمي. تتعامل طبقة الوكيل مع كل ما لا تستطيع وصفات OpenRewrite التعامل معه: عمليات إعادة الكتابة الغامضة، وانجراف نظام البناء، وبناء الجملة الطويلة، وكسر التبعية المتعدية.
ستقوم بإنشاء وكيل يأخذ Java 8 repo (أو Python 2 repo) وينتج فرعًا مُرحَّلًا باللون الأخضر CI. ستقيس معدل النجاح، والحفاظ على تغطية الاختبار، وتكلفة الريبو، وبناء تصنيف الفشل. يخبرك خط الأساس الحتمي فقط جنبًا إلى جنب بالمكان الذي تعيش فيه قيمة الوكيل فعليًا.
## مفهوم
يحتوي الخط pipeline على طبقتين. تعمل **الركيزة الحتمية** (OpenRewrite لـ Java، وlibcst لـ Python) على تشغيل الجزء الأكبر من عمليات إعادة الكتابة الميكانيكية بأمان: عمليات الاستيراد، وتوقيعات الطريقة، والتحريرات الخالية من الأمان، والتجربة باستخدام الموارد، واستبدالات API المهملة. إنه سريع وينتج فروقًا قابلة للتدقيق. تتعامل **طبقة الوكيل** (OpenAI Agents SDK أو LangGraph over Claude Opus 4.7 وGPT-5.4-Codex) مع الحالات التي لا تستطيع الوصفات القيام بها: ترقيات ملف البناء (Maven/Gradle/pyproject)، وتعارضات التبعية المتعدية، ورقائق الاختبار، والتعليقات التوضيحية المخصصة.
يحصل كل ريبو على وضع حماية Daytona مع تثبيت وقت التشغيل المستهدف مسبقًا. يكرر الوكيل: تشغيل البناء، وتصنيف حالات الفشل، وتطبيق الإصلاح، وإعادة التشغيل. الحدود الصارمة: 30 دقيقة لكل ريبو، 8 دولارات لكل ريبو، 20 دورة للوكيل. إذا نجحت جميع الاختبارات ولم تكن دلتا التغطية سلبية، فسيفتح الفرع PR. إذا لم يكن الأمر كذلك، فسيتم تقديم الريبو تحت فئة الفشل مع الأدلة.
تصنيف الفشل هو التسليم. عبر 50 اتفاقا، ما الذي كسر؟ انخفاضات متعدية؟ التعليقات التوضيحية المخصصة؟ إصدار أداة البناء؟ رقائق الاختبار لا علاقة لها بالهجرة؟ يحصل كل فئة على عدد وفرق نموذجي. يمكن لمؤلفي الوصفات المستقبلية استهداف الثلاثة الأوائل.
## بنيان
```
target repo
      |
      v
OpenRewrite / libcst deterministic recipes
   (safe, fast, auditable, ~70-80% of fixes)
      |
      v
Daytona sandbox per branch
      |
      v
agent loop (Claude Opus 4.7 / GPT-5.4-Codex):
   - run build -> capture failures
   - classify failures (build, test, lint)
   - apply fix (patch or retry recipe)
   - rerun
   - budget: 30 min, $8, 20 turns
      |
      v
test + coverage delta gate
      |
      v (passed)
open PR
      |
      v (failed)
file under failure class + attach repro
```

## المكدس
- الركيزة الحتمية: OpenRewrite (Java) أو libcst (Python)
- الوكيل: OpenAI Agents SDK أو LangGraph over Claude Opus 4.7 + GPT-5.4-Codex
- Sandbox: حاويات تطوير Daytona لكل فرع، وقت تشغيل مستهدف مثبت مسبقًا (Java 17 / Python 3.12)
- أنظمة البناء: Maven، Gradle، uv (Python)
- المعايير: مجموعة Amazon MigrationBench 50-repo الفرعية (Java 8 إلى 17)، وGoogle App Engine Py2-to-Py3 repos
- أدوات الاختبار: تشغيل متوازي، تغطية عبر Jacoco (Java) أو Coverage.py (Python)
- إمكانية الملاحظة: Langfuse + حزمة التتبع لكل ريبو مع كل قطعة مختلفة
- لوحة المعلومات: لوحة معلومات لتصنيف الفشل مع أعداد لكل فئة واختلافات نموذجية
## بنائها
1. **تمرير الوصفة.** قم بتشغيل وصفات OpenRewrite (Java) أو libcst (Python) أولاً. احصل على 70-80% من الهجرات الميكانيكية. الالتزام كالتزام "وصفة".
2. ** تجربة البناء. ** وضع حماية Daytona: تثبيت وقت التشغيل المستهدف، وتشغيل الإنشاء. إذا كان أخضر، فانتقل إلى الاختبارات. إذا كان اللون أحمر، سلمه إلى الوكيل.
3. **حلقة الوكيل.** LangGraph مع الأدوات: `run_build`، `read_file`، `edit_file`، `run_test`، `git_diff`. يقوم الوكيل بتصنيف الفشل (dep، وبناء الجملة، والاختبار، وأداة البناء) ويطبق الإصلاح المستهدف. أعد التشغيل.
4. **الحد الأقصى للميزانية.** 30 دقيقة من ساعة الحائط لكل اتفاقية ريبو، بتكلفة 8 دولارات، و20 دورة للوكيل. يتوقف أي خرق ويتم الملفات ضمن "budget_exhausted" مع الفرق الحالي.
5. **بوابة الاختبار + التغطية.** بعد أن يتحول التصميم إلى اللون الأخضر، قم بتشغيل مجموعة الاختبار. قارن التغطية بالريبو الأساسي. إذا انخفضت التغطية بأكثر من 2%، قم بالتسجيل ضمن "coverage_regression".
6. **PR مفتوح.** عند النجاح، ادفع الفرع، افتح PR مع الفرق وملخص الوصفات المطبقة والتي يلزم الوكيل بتأليفها.
7. **تصنيف الفشل.** لكل إعادة شراء فاشلة، ضع علامة بفئة: `dep_upgrade_required`، `build_tool_drift`، `custom_annotation`، `test_flake`، `syntax_edge_case`، `budget_exhausted`. بناء لوحة القيادة.
8. **تشغيل 50-ريبو.** تنفيذ عبر مجموعة MigrationBench الفرعية. قم بالإبلاغ عن معدل النجاح لكل فئة، وتكلفة إعادة الشراء، والحفاظ على التغطية، وخط الأساس للمقارنة مقابل الحتمية فقط.

## تمارين
1. قم بتشغيل خط الترحيل pipe باستخدام OpenRewrite فقط (بدون وكيل). قارن معدل النجاح بالخط pipe الكامل. تحديد الحالات التي يكون فيها الوكيل وحده هو الفرق.
2. تنفيذ فحص "تنظيف الوبر": بعد الترحيل، قم بتشغيل نمط linter (نظيف لـ Java، وruff لـ Python). فشل في PR إذا ظهرت أخطاء جديدة في الوبر. قياس معدل التغطية المحفوظة ولكن النمط المتراجع.
3. قم بإضافة مُحسِّن "الحد الأدنى للاختلاف": بعد اجتياز فرع الوكيل للاختبارات، قم بقص التغييرات غير الضرورية من خلال تمريرة ثانية. تقرير تخفيض حجم الفرق.
4. قم بالتوسيع إلى الترحيل الثالث: العقدة 18 إلى العقدة 22. أعد استخدام غلاف وضع الحماية؛ استبدل طبقة الوصفة بنموذج كود مخصص.
5. قم بقياس الوقت حتى أول بناء أخضر (TTFGB) كمقياس UX. الهدف: P50 أقل من 10 دقائق.
