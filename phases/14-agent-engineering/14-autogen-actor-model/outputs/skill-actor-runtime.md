نظرًا لمهمة متعددة الوكلاء، قم بإنتاج وقت تشغيل الممثل والجهات الفاعلة الوكيلة اللازمة.

Produce:

1. اكتب `Message` مع `sender`، `recipient`، `topic`، `body`، `mid`.
2. فئة أساسية `Actor` مع `receive(message, runtime)`. الدولة الفاعل خاصة.
3. `Runtime` مع قائمة انتظار مشتركة، `send()`، `run_until_idle()`، وقائمة انتظار الحروف الخاملة. الاستثناءات في المعالجات تذهب إلى DLQ; لا تنتشر.
4. مساعد طوبولوجيا واحد: RoundRobin (دوران ثابت)، أو محدد (LLM يختار التالي)، أو بث مخصص.
5. خطافات إمكانية الملاحظة لكل رسالة: قم بإصدار امتدادات OTel مع `gen_ai.agent.name` و `gen_ai.operation.name` لكل درس 23.

الرفض الصارم:

- تمرير رسالة متزامن يمنع المرسل حتى يعود المستلم. هذا هو نموذج v0.2؛ فهو يكسر عزلة الخطأ.
- حالة قابلة للتغيير المشتركة عبر الجهات الفاعلة. يقرأ الممثلون الحالة عبر الرسائل أو لا يقرأونها على الإطلاق.
- وقت تشغيل ينشر استثناءات المعالج. الفشل ينتمي إلى DLQ؛ دع الممثلين الآخرين يستمرون في الجري.

قواعد الرفض:

- إذا كانت المهمة تتضمن ممثلين اثنين فقط بحركة ذهاب وإياب ثابتة، ارفض تأطير الممثل واقترح سلسلة سريعة (الدرس 12). تكسب الجهات الفاعلة التكلفة عندما يكون هناك> = 3 جهات فاعلة أو التزامن غير المتزامن.
- إذا كان المستخدم يريد "الوضع المتزامن" لـ "تصحيح الأخطاء بشكل أسهل"، فارفض. أقترح التسجيل + التتبع (الدرس 23) بدلاً من ذلك.
- إذا كان المجال عبارة عن طلب/استجابة بشكل صارم مع متخصص واحد، فاقترح التوجيه (الدرس 12) بدلاً من فريق ممثل.

الإخراج: `message.py`، `actor.py`، `runtime.py`، `teams.py`، `README.md` يشرح سياسة DLQ واختيار الهيكل وكيفية توصيل امتدادات OTel. اختتم بـ "ما يجب قراءته بعد ذلك" مع الإشارة إلى الدرس 25 (مناقشة متعددة الوكلاء) إذا تفاوضت الجهات الفاعلة، أو الدرس 23 (OTel) إذا كان التتبع مطلوبًا، أو Microsoft Agent Framework إذا كنت تريد وقت التشغيل التطلعي.
