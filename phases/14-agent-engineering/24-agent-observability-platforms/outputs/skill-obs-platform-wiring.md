بالنظر إلى وقت تشغيل الوكيل ومتطلبات المنتج، اختر منصة قابلة للمراقبة وقم بدعم الأسلاك.
قرار:
1. تحتاج إلى إدارة سريعة + إعادة تشغيل الجلسة في مكان واحد -> **Langfuse**.
2. تحتاج إلى صلة عميقة بـ RAG + اكتشاف الانحراف/الشذوذ -> **Phoenix**.
3. تحتاج إلى تحسين فوري تلقائي + PII حواجز الحماية -> **Opik**.
4. قم بالفعل بتشغيل Datadog -> **Datadog LLM إمكانية المراقبة** (خرائط GenAI أصلاً من الإصدار 1.37+).
5. تحتاج إلى ترخيص مجاني لـ ELv2 -> **Langfuse** (MIT) أو **Opik** (Apache 2.0)؛ تجنب Phoenix للتوزيع OSS النقي.
ينتج:
1. أدوات OTel GenAI (الدرس 23) – هذه هي الركيزة المشتركة.
2. تكوين SDK أو مصدر OTel الخاص بالمنصة.
3. LLM-حكم على نطاقك (الصحة الواقعية، النطاق، اللهجة، جودة الرفض).
4. إصدار سريع موصول بتتبعات (Langfuse) أو تتبع تكوين المجموعات (Phoenix) أو تعريفات التجربة (Opik).
5. حواجز الحماية على المحتوى المسجل: PII التنقيح والتنقيح السري.
6. لوحات المعلومات: صحة الجلسة، وتصنيف الفشل، وتوزيع زمن الوصول، والتكلفة لكل جلسة.
الرفض الصارم:
- الشحن بدون تقييم. التتبع وحده هو عملية قطع الأشجار باهظة الثمن.
- استخدام حكم مكتوب ذاتيًا LLM بدون أي تحقق خارجي. نمط CRITIC (الدرس 05): يحتاج القضاة إلى أدوات خارجية للتأريض الواقعي.
- تخزين PII في الأجسام الممتدة. دائمًا متجر خارجي + معرفات مرجعية.
قواعد الرفض:
- إذا طلب المستخدم "منصة واحدة لكل شيء"، ارفض واعرض القرار أعلاه. لا توجد منصة واحدة تهيمن على المحاور الثلاثة.
- إذا لم يكن للمنتج معايير قبول لكل مهمة وكيل، فارفض شحن التقييمات. يحتاج القاضي LLM- إلى عنوان تقييم؛ يحتاج نموذج التقييم إلى قرارات تتعلق بالمنتج.
- إذا كان المستخدم يريد "عدم أخذ العينات، والتقاط كل شيء"، ارفض. تتبع حجم المقاييس خطيا مع حركة المرور؛ أخذ العينات (على أساس الرأس أو على أساس الذيل) مطلوب على نطاق واسع.
الإخراج: `instrumentation.py`، `judge.py`، `dashboards.md`، `README.md` شرح اختيار النظام الأساسي، وقواعد التقييم، واستراتيجية أخذ العينات، والاستجابة للحوادث. اختتم بـ "ما يجب قراءته بعد ذلك" مع الإشارة إلى الدرس 30 (التطوير القائم على التقييم) أو الدرس 26 (تصنيف وضع الفشل).
