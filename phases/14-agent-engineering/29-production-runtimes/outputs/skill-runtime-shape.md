بالنظر إلى فئة المهمة (المدة المتوقعة، عدد الخطوات، نوع المشغل، ميزانية وقت الاستجابة)، اختر شكل وقت التشغيل.

Decision:

1. < 30 ثانية، ينتظر المستخدم -> **الاستجابة للطلب**.
2. التقدمي UX أو الصوت -> **البث**.
3. من دقائق إلى ساعات، لا ينتظر المستخدم -> **معتمد على قائمة الانتظار**.
4. تفاعل مع الأحداث الخارجية -> **مدفوع بالحدث**.
5. التدبير المنزلي الدوري -> **كرون**.
6. أي مما سبق حيث تكون تكلفة إعادة التشغيل مرتفعة -> أضف **التنفيذ الدائم**.

Produce:

1. سقالة الشكل في مجموعتك.
2. إمكانية الملاحظة: امتدادات OTel GenAI (الدرس 23)، الواجهة الخلفية السلكية (الدرس 24).
3. بالنسبة لقائمة الانتظار: DLQ + سياسة إعادة المحاولة + مقياس عمق قائمة الانتظار.
4. بالنسبة للحدث: تسجيل مشترك صريح + مسار إعادة التشغيل.
5. بالنسبة إلى cron: قفل الملف أو القفل الموزع لمنع تداخل عمليات التشغيل.
6. من أجل المتانة: الواجهة الخلفية لنقطة التفتيش + دلالات السيرة الذاتية.

الرفض الصارم:

- متزامن HTTP لمهمة مدتها 5 دقائق. يغلق المستخدمون المكالمة؛ العمال يتراكمون.
- قائم على قائمة الانتظار بدون DLQ. الوظائف الفاشلة تختفي.
- العمل في الخلفية بدون تصدير أثر. الفشل غير مرئي حتى يشتكي المستخدمون.
- "لا توجد حالة دائمة، سنحاول فقط". الآفاق البعيدة لا بد من نقطة تفتيش.

قواعد الرفض:

- إذا كان المنتج يحتوي على SLA + متطلبات إعادة التشغيل، فارفض طوبولوجيا السرب + وقت التشغيل غير الدائم.
- إذا كانت المهمة ملزمة بالامتثال، فارفضها بناءً على الأحداث دون إجراء تدقيق.
- إذا كان المستخدم يريد cron + no lock، ارفض. يعد تشغيل cron المتداخل بمثابة عمل مكرر في أحسن الأحوال، وتلف البيانات في أسوأ الأحوال.

الإخراج: سقالة وقت التشغيل + خطافات إمكانية الملاحظة + README مع SLA، سياسة إعادة المحاولة، اختيار نقطة التفتيش. اختتم بـ "ما يجب قراءته بعد ذلك" بالإشارة إلى الدرس 23 (OTel)، أو الدرس 24 (إمكانية الملاحظة)، أو الدرس 17 (الوكلاء المُدارون للاستضافة الطويلة الأمد).
