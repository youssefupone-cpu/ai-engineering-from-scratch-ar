# قائمة مراجعة الإنتاج LLM
عند شحن تطبيق LLM، تعامل مع قائمة التحقق هذه بالترتيب. يحتوي كل قسم على معايير النجاح/الفشل مع حدود محددة.
## 1. الأمن (حاصرات السفن)
يجب أن يمر كل عنصر هنا قبل أي عملية نشر.
| تحقق | معايير النجاح | كيفية التحقق |
|-------|-------------|---------------|
| API مفاتيح في env vars | صفر مفاتيح مضمنة في قاعدة التعليمات البرمجية | `grep -r "sk-" --include="*.py"` لا يُرجع شيئًا |
| حواجز حماية الإدخال نشطة | أنماط الحقن الفوري منعت | إرسال "تجاهل جميع التعليمات السابقة" - يُرجع الاستجابة المحظورة |
| PII تنقيح | SSN، بطاقة الائتمان، أنماط البريد الإلكتروني التي تم اكتشافها | أرسل "SSN الخاص بي هو 6789-45-123" -- تم تنقيح PII قبل مكالمة LLM |
| تصفية الإخراج | محتوى خطير تم حظره | لا يمكن للنموذج إرجاع أنماط `DROP TABLE`، `rm -rf`، `exec()` |
| الحد من المعدل | تم فرض الحد الأقصى للطلب لكل مستخدم | 100 طلب من نفس المستخدم في 10 ثوانٍ - تم رفض آخر 50+ |
| المصادقة على كافة نقاط النهاية | لا يوجد وصول غير مصادق عليه LLM | `curl /v1/chat` بدون رمز مميز يُرجع 401 |
| CORS مقيد | مجالات الإنتاج المسموح بها فقط | تم رفض طلب `Origin: evil.com` |
| الحد الأقصى لرموز الإدخال | تم رفض الطلبات التي تتجاوز الحد | إرسال إدخال رمزي بقيمة 50 ألفًا - إرجاع 413 أو الاقتطاع |
## 2. الموثوقية (البقاء لمدة أسبوع واحد)
هذه تمنع وقوع أول حادث عند الطلب.
| تحقق | معايير النجاح | كيفية التحقق |
|-------|-------------|---------------|
| أعد المحاولة مع التراجع | 3 محاولات في 5xx، تأخير أسي | قم بإنهاء LLM في منتصف الطلب الوهمي - تظهر عمليات إعادة المحاولة في السجلات |
| سلسلة النموذج الاحتياطي | 2+ نماذج في السلسلة | النموذج الأساسي غير متوفر - لا تزال الاستجابة ترجع من الإجراء الاحتياطي |
| طلب مهلة | 30 ثانية كحد أقصى لجميع المكالمات الخارجية | نموذج LLM بطيء (60 ثانية) - تنتهي مهلة الطلب عند 30 ثانية |
| انحطاط رشيق | فشل ذاكرة التخزين المؤقت/RAG لا يؤدي إلى تعطل الخدمة | إيقاف ذاكرة التخزين المؤقت - لا تزال الطلبات تنجح (أبطأ وأكثر تكلفة) |
| نقطة نهاية فحص الصحة | إرجاع حالة التبعية | `GET /health` يُرجع `{"status": "healthy", "cache": ..., "llm": ...}` |
| أعمال الجري | الرمز الأول أقل من 500 مللي ثانية | تم قياس الوقت حتى أول رمز مميز، باستمرار <500 مللي ثانية |
| رسائل الخطأ آمنة | الأخطاء الداخلية لا تتسرب أبدًا إلى المستخدمين | القوة 500 - يرى المستخدم خطأً عامًا، وليس تتبع المكدس |
## 3. التحكم في التكاليف (اقتصاديات الشهر الأول)
يمنع هذا الفاتورة المفاجئة بقيمة 50 ألف دولار.
| تحقق | معايير النجاح | كيفية التحقق |
|-------|-------------|---------------|
| تتبع التكلفة لكل طلب | يقوم كل طلب بتسجيل عدد الرموز المميزة + USD التكلفة | يحتوي سجل الطلب على `input_tokens`، `output_tokens`، `cost_usd` الحقول |
| ذاكرة التخزين المؤقت الدلالية نشطة | > معدل نجاح 20% على الأنماط المتكررة | تُظهر إحصائيات ذاكرة التخزين المؤقت معدل الإصابة بعد 1000 طلب اختبار |
| تم تكوين ذاكرة التخزين المؤقت TTL | تنتهي صلاحية الإدخالات (الافتراضي: ساعة واحدة) | تم إدراج الإدخال - ولم يتم إرجاعه بعد TTL |
| تتبع التكلفة لكل مستخدم | التكلفة مجمعة بواسطة user_id | لوحة المعلومات/API تعرض أفضل 10 مستخدمين حسب التكلفة |
| تنبيه التكلفة | تنبيه بنسبة 80% من الميزانية اليومية | حدد ميزانية يومية بقيمة 10 دولارات، وأرسل طلبات بقيمة 8.50 دولارًا - تنبيه ينطلق |
| توجيه النموذج حسب التكلفة | تستخدم الاستعلامات منخفضة التعقيد نموذجًا أرخص | طرق الأسئلة البسيطة إلى gpt-4o-mini، والمعقدة إلى gpt-4o |
| مجموعة الرموز المميزة القصوى | الردود محددة لكل قالب | قالب يحتوي على max_output_tokens=512 - الاستجابة لا تتجاوزه أبدًا |
**صيغة تقدير التكلفة:**```
Monthly LLM cost = DAU x queries_per_user x 30 x (1 - cache_hit_rate) x (avg_input_tokens x input_price + avg_output_tokens x output_price) / 1,000,000
```

**العتبات المرجعية حسب المقياس:**
| DAU | التكلفة المستهدفة / الطلب | الميزانية الشهرية |
|-----|-------------------|----------------|
| 1 ك | < 0.005 دولار | < 750 دولارًا |
| 10 الف | < 0.003 دولار | < 4,500 دولار |
| 100 ألف | < 0.001 دولار | < 15,000 دولار |
## 4. إمكانية الملاحظة (تصحيح الأخطاء في الإنتاج)
لا يمكنك إصلاح ما لا يمكنك رؤيته.
| تحقق | معايير النجاح | كيفية التحقق |
|-------|-------------|---------------|
| تسجيل منظم JSON | ينتج عن كل طلب سطر سجل JSON | يحتوي السجل على: request_id، user_id، النموذج، الرموز المميزة، latency_ms، التكلفة |
| طلب التتبع | تتبع شامل مع توقيت المكون | يُظهر الطلب الفردي: حاجز حماية (5 مللي ثانية) + ذاكرة تخزين مؤقت (2 مللي ثانية) + llm (3200 مللي ثانية) + تقييم (1 مللي ثانية) |
| تتبع الكمون | P50، P95، P99 مُقاس | بعد 1000 طلب: P50 <2s، P99 <10s |
| مراقبة معدل الخطأ | عد الأخطاء وتصنيفها | تعرض لوحة المعلومات: 0.5% API أخطاء، 0.1% كتل حماية، 0.01% مهلة |
| مقاييس ذاكرة التخزين المؤقت | معدل الإصابة، معدل الفشل، عدد الإدخالات مرئي | `GET /v1/cache/stats` يُرجع الأرقام الحالية |
| مقاييس اختبار أ/ب | تم تسجيل مقاييس الجودة لكل متغير | يسجل كل طلب إصدار Prompt_template + للمقارنة |
| تسجيل التقييم | إشارات الجودة المسجلة لكل طلب | طول الاستجابة، زمن الوصول، النموذج، إصدار القالب المخزن للتحليل دون اتصال |
## 5. الإدارة السريعة
المطالبات هي رمز. عاملهم مثل الكود.
| تحقق | معايير النجاح | كيفية التحقق |
|-------|-------------|---------------|
| قوالب منقحة | كل قالب له اسم + سلسلة إصدار | يؤدي تغيير القالب إلى إنشاء إصدار جديد، مع الاحتفاظ بالإصدار القديم |
| دعم اختبار أ/ب | تقسيم حركة المرور حسب تجزئة المستخدم الحتمية | يرى نفس المستخدم دائمًا نفس المتغير داخل التجربة |
| القدرة على التراجع | العودة إلى الإصدار السابق في أقل من دقيقة واحدة | تغيير تكوين التجربة - تتحول حركة المرور على الفور |
| التحقق من صحة القالب | تم التحقق من صحة المتغيرات قبل العرض | يؤدي فقدان المتغير في القالب إلى ظهور خطأ واضح، وليس KeyError |
| نظام الفصل السريع | رسائل النظام والمستخدم في حقول منفصلة | لم يتم دمج موجه النظام في رسالة المستخدم |
## 6. الاستعداد للقياس
ليست هناك حاجة عند الإطلاق. مطلوب في 10x.
| تحقق | معايير النجاح | كيفية التحقق |
|-------|-------------|---------------|
| مكالمات غير متزامنة LLM | لا يوجد حظر لسلسلة الرسائل في مكالمات API | 50 طلبًا متزامنًا - يبقى الخادم CPU <30% |
| تجمع الاتصال | HTTP إعادة استخدام الاتصالات | يُظهر تتبع الشبكة الاتصالات المستمرة بموفر LLM |
| التحجيم الأفقي | تصميم خادم عديم الحالة | حالتان خلف موازن التحميل - تنجح جميع الطلبات |
| دعم قائمة الانتظار | يتم نقل المهام غير في الوقت الحقيقي إلى قائمة الانتظار | يقوم طلب التلخيص بإرجاع job_id، والنتيجة متاحة عبر الاقتراع |
| تم اختبار التحميل | 100 مستخدم متزامن، <5% معدل خطأ | يمر اختبار `wrk` أو `locust` بالتزامن المستهدف |
##أمر التنفيذ للمشاريع الجديدة
1. **اليوم الأول:** خادم API + قوالب المطالبة + مكالمة LLM فردية مع إعادة المحاولة
2. **اليوم الثاني:** حواجز حماية الإدخال + حواجز حماية الإخراج + معالجة الأخطاء
3. **اليوم الثالث:** ذاكرة التخزين المؤقت الدلالية + تتبع التكلفة لكل طلب
4. **اليوم 4:** البث (SSE) + نقطة نهاية التحقق من الصحة
5. **اليوم الخامس:** التسجيل المنظم + تتبع الطلب + تسجيل التقييم
6. **الأسبوع 2:** اختبار A/B + الإصدار الفوري + التراجع
7. **الأسبوع 3:** سلسلة النماذج الاحتياطية + التدهور الرائع
8. **الأسبوع 4:** اختبار التحميل + تحسين عدم التزامن + القياس الأفقي
## التشخيص السريع
إذا كان هناك خطأ ما في الإنتاج، فتحقق من هذا الترتيب:
1. **هل يشتكي المستخدمون من الأخطاء؟** تحقق من نقطة النهاية الصحية، ثم معدل الخطأ في السجلات، ثم LLM صفحة حالة الموفر
2. **الاستجابات بطيئة؟** تحقق من زمن الاستجابة P99، ثم معدل الدخول إلى ذاكرة التخزين المؤقت، ثم LLM أوقات الاستجابة في عمليات التتبع
3. **ارتفاع التكلفة؟** تحقق من اتجاه التكلفة لكل طلب، ثم معدل ضربات ذاكرة التخزين المؤقت، ثم أعلى المستخدمين حسب التكلفة، ثم ابحث عن تغييرات القالب السريعة التي أدت إلى زيادة عدد الرموز المميزة
4. **انخفضت الجودة؟** تحقق مما إذا تم نشر إصدار موجه جديد، وتحقق مما إذا كانت دقة الاسترداد RAG قد تغيرت، وتحقق مما إذا كان موفر النموذج قد قام بتغيير إصدار النموذج الافتراضي
5. **حادث أمني؟** تحقق من معدل حظر حاجز الحماية (السقوط المفاجئ = تعطيل حاجز الحماية)، وتحقق من سجلات الطلبات بحثًا عن أنماط غير عادية، وقم بتدوير مفاتيح API على الفور
