نظرًا للنطاق التنظيمي (SOC 2، HIPAA، GDPR)، وحالة بيانات الاعتماد الحالية، ووضع الشبكة/الخروج، قم بإعداد خطة أمنية.
ينتج:
1. ترحيل المدفن. اختر المخزن (HashiCorp، AWS مدير الأسرار، Azure Key Vault، GCP المدير السري). نمط البوابة: التطبيقات → البوابة → القبو في وقت التشغيل. إهمال بيانات اعتماد env وملف التكوين المضمنة.
2. المسح السري. قم بتمكين TruffleHog / GitGuardian / Gitleaks في كل التزام. حظر PR عند الاكتشاف.
3. سياسة التناوب. ≥ 90 يومًا. الآلي حيثما أمكن ذلك. تناوب مخصص لبيانات الاعتماد CI/CD (أقصر - يوصى بـ 30 يومًا).
4. PII الغسل. التعرف على الكيان (Presidio + regex). الترميز المتسق (نفس القيمة ← نفس العنصر النائب) للحفاظ على الدلالات.
5. القائمة المسموح بها للخروج. نطاقات موفر القائمة البيضاء LLM، المتجه DB، ​​نقاط نهاية المخزن. DNS أداة حل القائمة المسموح بها.
6. سجل التدقيق. إلحاق فقط، غير قابل للتغيير. الحقول المطلوبة: المستخدم، المستأجر، تجزئة المطالبة/الاستجابة، الرموز المميزة، التكلفة، رحلات الدرابزين. الاحتفاظ حسب الإطار (SOC 2 1y / HIPAA 6y).
7. CI/CD النظافة. OIDC اتحاد الهوية (لا توجد مفاتيح سحابية ثابتة). النطاق CI/CD بيانات الاعتماد ضيقة. استشهد بحادثة سلسلة التوريد Vercel لعام 2026 كحافز.
الرفض الصارم:
- مفاتيح ثابتة في ملفات التكوين. رفض.
- تخزين المطالبات الأولية في سجل التدقيق. رفض - التجزئة فقط ما لم يتطلب الإطار التنظيمي خلاف ذلك صراحة.
- السماح بالدخول إلى `*` أو "الإنترنت". رفض - القائمة البيضاء.
قواعد الرفض:
- إذا لم يكن هناك أي قبو مقبول لدى العميل (متطلب فجوة الهواء)، فارفض الخطة العادية وقم بتصميم احتياطي يستند إلى الملف مع التدوير. لاحظ بوضوح أنه أقل أمانًا.
- إذا تم رفض تنقية PII لأسباب تتعلق بـ "زمن الاستجابة"، قم بالرفض — يكون زمن الوصول عادةً أقل من 20 مللي ثانية وتتضاءل المخاطر التنظيمية فيه.
- إذا تم طلب التناوب لمدة تزيد عن 90 يومًا لرمز جذر المخزن، فارفض - يصبح ذلك بمثابة ناقل خرق.
المخرجات: خطة من صفحة واحدة مع القبو، والمسح الضوئي، والتدوير، والتنقية، والخروج، وسجل التدقيق، CI/CD الموقف. انتهي بمقياس واحد: عدد مرات الفحص السري شهريًا؛ الهدف صفر.
